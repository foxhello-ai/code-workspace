# Backlog

## B-001: 多浏览器 Tab 独立工作区

### 状态

- 提出日期：2026-07-21
- 状态：已实现
- 优先级：中

### 背景

当前产品采用“单进程、单活动工作区”模型。服务端只有一个全局 `WorkspaceService.current`，所有浏览器 Tab 共享同一个后端当前工作区。

### 问题现象

用户在浏览器中打开两个 Tab 后，如果其中一个 Tab 切换工作区，另一个 Tab 也会在刷新或再次请求接口后看到同一个新工作区。

这会导致以下体验问题：

- 无法在两个浏览器 Tab 中同时查看两个不同工作区。
- 一个 Tab 的工作区切换会影响另一个 Tab 的文件树、Git 状态、历史记录和事件订阅。
- 如果两个 Tab 正在处理不同任务，用户容易误以为它们互相独立，从而产生操作混淆。

### 已确认原因

服务端当前工作区是全局单例状态：

- `WorkspaceService.current` 只保存一个 `WorkspaceContext`。
- `/api/workspace/open` 会覆盖全局当前工作区。
- `/api/files/*`、`/api/git/*`、`/api/events` 默认读取同一个全局当前工作区。
- 前端每个浏览器 Tab 没有独立的 `sessionId` 或 `workspaceId` 作用域。

### 影响范围

如果要支持多 Tab 独立工作区，需要调整以下模块：

- 服务端工作区状态：从单个 `current` 改为按会话隔离的 `Map<sessionId, WorkspaceContext>`。
- API 契约：文件、Git、事件接口需要携带或解析当前 Tab 的 `sessionId`。
- Watcher 生命周期：每个活动工作区需要独立 watcher，并需要设置资源上限和回收策略。
- Git 缓存：状态缓存、revision、当前选中 Git 仓库需要按会话隔离。
- 前端状态：使用 `sessionStorage` 为每个浏览器 Tab 保存独立 `sessionId`。
- 关闭策略：支持关闭单个 Tab 对应的工作区，并在浏览器关闭后清理后端资源。

### 建议方案

1. 前端首次加载时生成 `sessionId`，保存到 `sessionStorage`。
2. 所有 API 请求通过 header 或 query 传递 `sessionId`。
3. 服务端用 `WorkspaceSessionService` 管理多个工作区上下文。
4. `WorkspaceService` 降级为单个工作区上下文的操作对象，避免继续承载全局状态。
5. watcher 和 GitService 改为按 `sessionId + repositoryId` 隔离。
6. 为 session 增加空闲超时和显式关闭逻辑，防止长期打开多个大型目录造成资源泄漏。

### 验收标准

- 同一浏览器打开两个 Tab，分别打开两个不同工作区，互不覆盖。
- Tab A 切换工作区后，Tab B 的文件树、Git 仓库选择、历史记录不变化。
- Tab A 的 WebSocket 事件只影响 Tab A 对应工作区。
- 关闭 Tab 或点击“切换/关闭工作区”时，只清理当前 Tab 对应 session。
- 多工作区同时打开时，PM2 进程资源不会无上限增长。

### 当前使用说明

现在可以在不同浏览器 Tab 中打开不同工作区。每个 Tab 的工作区、Git 当前项目、文件树和事件订阅按 Tab session 隔离。

### 实现记录

- 前端为每个浏览器 Tab 生成并传递独立 session 标识。
- 服务端按 session 隔离工作区、Git 服务、事件中心和文件 watcher。
- WebSocket 事件订阅按 session 绑定当前工作区，避免 Tab 间互相污染。

## B-002: 文件树右键复制和查看本地路径

### 状态

- 提出日期：2026-07-21
- 状态：已实现
- 优先级：中

### 背景

当前文件树可以浏览、打开、编辑文件，也能通过接口解析文件的绝对路径。但界面上缺少直接复制文件或文件夹本地路径的入口。用户想把路径粘贴到终端、编辑器、外部工具或沟通消息中时，需要手动拼接工作区路径和相对路径，效率低且容易出错。

### 问题现象

用户在文件树中看到目标文件或文件夹后，没有明显位置可以复制它的本地路径。

典型场景：

- 想把某个文件路径复制到终端命令中。
- 想把某个文件夹路径发给其他工具处理。
- 想确认符号链接条目的实际可访问路径。
- 想复制相对工作区路径，用于项目内文档、Git Diff 或搜索定位。

### 需求整理

在文件树条目上增加右键菜单，至少支持以下操作：

- 复制绝对路径：复制该文件或文件夹在本机文件系统中的绝对路径。
- 复制工作区相对路径：复制相对当前工作区根目录的路径。
- 查看本地路径：以只读方式展示绝对路径，便于用户确认后手动选择复制。

对文件和文件夹都应支持上述能力。符号链接条目需要明确路径语义，默认复制用户在工作区中看到的逻辑路径对应的本地路径；如后续需要，也可增加“复制链接目标路径”。

### 交互建议

1. 用户在文件树文件或文件夹条目上右键。
2. 弹出轻量上下文菜单。
3. 菜单项包含“复制绝对路径”“复制相对路径”“查看本地路径”。
4. 复制成功后给出短提示，例如“已复制路径”。
5. 如果浏览器剪贴板 API 不可用，降级为打开“查看本地路径”弹层，让用户手动复制。
6. 菜单应在点击外部、按 `Escape`、滚动或切换工作区时关闭。

### 影响范围

- 前端文件树组件：增加右键事件和上下文菜单状态。
- 前端提示系统：复用当前 notice 或增加轻量 toast。
- 后端路径接口：可复用 `/api/files/absolute-path?path=...`，避免前端自行拼接绝对路径。
- 安全边界：绝对路径仍必须通过后端 PathGuard 校验，不能允许前端构造越界路径。
- 符号链接行为：需要与现有 symlink 展示逻辑保持一致。

### 验收标准

- 文件条目右键后能复制绝对路径。
- 文件夹条目右键后能复制绝对路径。
- 文件和文件夹都能复制工作区相对路径。
- “查看本地路径”展示的是后端校验后的绝对路径。
- 复制路径后有明确成功提示。
- 对符号链接文件和符号链接文件夹，复制/查看路径不会报错。
- 右键菜单不会遮挡文件树主要操作，也不会影响单击展开文件夹和打开文件。
- 路径中包含空格、中文或特殊字符时复制内容保持完整。

### 当前处理建议

该需求适合作为一次前端交互增强独立实现。实现时优先使用现有 `/api/files/absolute-path` 接口，不扩大文件系统访问权限。

### 实现记录

- 文件树条目支持右键菜单。
- 支持复制绝对路径、复制相对路径、查看本地路径。
- 绝对路径通过后端 PathGuard 校验后的接口返回。

## B-003: Git 历史提交列表、提交详情和 Diff 同屏联动

### 状态

- 提出日期：2026-07-21
- 状态：已实现
- 优先级：中

### 背景

当前 Git 历史面板支持提交图、线性列表、提交详情和提交文件 Diff。但交互上是单面板替换式流程：用户点击某个提交后，历史列表或提交图被提交详情替换；想查看另一个提交时，需要先点击“返回历史”，再重新选择提交。提交文件 Diff 又会打开到编辑区标签页，提交详情和 Diff 不在同一个连贯界面中。

### 问题现象

用户查看不同提交的提交详情时，需要频繁在“历史列表/提交图”和“提交详情”之间来回切换。

典型问题：

- 无法一边保留提交列表，一边查看当前选中提交详情。
- 对比多个提交时，每次都要返回列表再选择另一个提交。
- 提交详情中的文件 Diff 打开到编辑区后，历史列表、提交详情、Diff 的上下文被拆散。
- 用户很难连续浏览“提交记录 → 提交详情 → 文件变更内容”。

### 已确认原因

当前前端实现中，`HistoryPanel` 使用 `selected` 状态做条件渲染：

- 未选中提交时展示提交图或历史列表。
- 选中提交且详情加载完成后，直接用 `CommitDetails` 替换列表区域。
- `CommitDetails` 通过“返回历史”按钮清空 selected。
- 文件 Diff 通过 `onDiff` 打开到主编辑区 tab，而不是在历史工作区内联动展示。

### 需求整理

希望 Git 历史能力改为同屏联动体验，让提交列表、提交详情、提交文件列表和 Diff 比对可以同时存在或保持上下文。

至少应支持：

- 提交列表或提交图始终可见。
- 点击提交后，在相邻区域展示提交详情，不替换掉列表。
- 选中不同提交时，详情区域直接刷新，不需要返回。
- 提交详情中的文件列表可选择文件，并在同屏展示该文件 Diff。
- 当前选中的提交和文件有明显高亮。
- 保留打开 Diff 到编辑区标签页的能力，作为“放大查看”或“在编辑区打开”操作。

### 交互建议

桌面端建议使用三段式布局：

1. 左侧：提交图或提交列表。
2. 中间：选中提交详情和文件变更列表。
3. 右侧或主编辑区：选中文件 Diff 预览。

如果空间不足，可以使用上下分栏：

1. 上方：提交列表。
2. 下方左侧：提交详情和文件列表。
3. 下方右侧：Diff 预览。

移动端或窄屏可以保留分步模式，但需要提供更轻量的返回和选中状态。

### 影响范围

- `src/web/App.tsx` 中 `HistoryPanel`、`CommitDetails`、`openDiff` 的交互关系。
- `src/web/styles.css` 中历史面板、提交详情和 Diff 预览布局。
- 前端状态：需要同时保存 `selectedCommitHash`、`selectedCommitDetail`、`selectedCommitFile`。
- API 可继续复用现有 `/api/git/history`、`/api/git/commits/:hash`、`/api/git/diff/commits/:hash`。
- Monaco DiffEditor 需要支持在历史区域内嵌展示，或复用现有 Diff tab 渲染逻辑。

### 验收标准

- 在 Git 历史页点击某个提交后，提交列表或提交图仍然可见。
- 连续点击不同提交时，详情区域直接更新，不需要先返回。
- 当前选中提交有明显视觉高亮。
- 提交详情展示 hash、作者、时间、提交说明、统计和文件列表。
- 点击提交文件后，同屏显示该文件 Diff。
- 当前选中文件有明显视觉高亮。
- 仍可将 Diff 打开到主编辑区标签页查看。
- 切换 Git 仓库后，选中提交、选中文件和 Diff 预览会正确清空或刷新。
- 没有提交、提交详情加载失败、Diff 内容过大或二进制文件时有明确空态或错误提示。

### 当前处理建议

该需求适合作为 Git 历史体验增强独立实现。实现前建议先确定桌面端目标布局，再决定移动端是否保留分步模式，避免一次改动同时重构历史、Diff 和移动端布局。

### 实现记录

- Git 历史列表/提交图保持可见。
- 选中提交后同屏展示提交详情和文件列表。
- 点击提交文件后直接在主编辑区打开 Diff，详情区不再额外展示内联 Diff。

## B-004: 编辑内容自动保存

### 状态

- 提出日期：2026-07-21
- 状态：已实现
- 优先级：中

### 背景

当前文本编辑需要用户手动点击“保存”按钮。用户在频繁切换文件、查看 Git 修改、查看历史或切换工作区时，容易忘记保存，导致编辑缓冲区长期处于未保存状态，增加丢失修改或误判 Git 状态的风险。

### 问题现象

用户修改文件后，如果没有点击保存按钮：

- Git 状态不会反映编辑器中的最新内容。
- 切换文件或处理其他任务时容易忘记当前文件未保存。
- 关闭页面或切换工作区前虽然有提示，但体验上仍需要用户手动兜底。
- 外部工具修改同一文件时，未保存缓冲区更容易产生冲突处理压力。

### 需求整理

希望增加编辑自动保存能力，减少用户忘记点击保存按钮的概率。

至少应支持：

- 文本文件修改后自动保存。
- 自动保存需要有防抖，不应每次键入都立即写盘。
- 自动保存过程中展示明确状态，例如“保存中”“已自动保存”“自动保存失败”。
- 如果磁盘文件已被外部修改，继续沿用现有 `409` 冲突保护，不自动覆盖外部修改。
- 用户仍可手动点击保存，手动保存应立即触发并取消等待中的自动保存。
- 自动保存失败后不丢弃编辑缓冲区。

### 交互建议

1. 用户编辑文本后，进入“等待自动保存”状态。
2. 停止输入一段时间后自动保存，例如 800-1500ms。
3. 保存成功后，状态栏显示“已自动保存”或恢复“已保存”。
4. 保存失败时，状态栏或冲突条展示错误原因。
5. 发生版本冲突时，自动保存停止，并展示现有冲突处理入口。
6. 可考虑提供设置项控制自动保存开关，默认开启或后续评审决定。

### 影响范围

- `src/web/App.tsx` 中编辑器 `onChange`、`save`、tab dirty 状态和 notice 状态。
- `src/web/store.ts` 中文本 tab 状态可能需要增加 `saveState`、`lastSavedAt` 或 `autoSaveError`。
- 文件保存 API 可继续复用现有 `PUT /api/files/content` 和 `expectedVersion`。
- 外部变更同步逻辑需要与自动保存协调，避免自动保存覆盖外部修改。
- 页面关闭、切换工作区、关闭标签页时的未保存提示策略需要重新评审。

### 风险和边界

- 自动保存是写操作，必须保留现有版本冲突保护。
- 自动保存不能对只读、大文件、二进制、未知编码文件生效。
- 自动保存失败不能清除 dirty 状态。
- 多标签打开同一文件时，需要避免旧 tab 自动保存覆盖新 tab 内容。
- 高频输入时要避免大量写盘和 Git watcher 事件抖动。

### 验收标准

- 修改普通 UTF-8 文本文件后，无需点击保存，停止输入后会自动写入磁盘。
- 自动保存期间有明确状态提示。
- 自动保存成功后，tab dirty 标记消失。
- Git 修改状态能反映自动保存后的磁盘内容。
- 手动点击保存会立即保存并取消待执行的自动保存。
- 外部修改同一文件后，自动保存返回冲突提示，不覆盖外部修改。
- 自动保存失败时，编辑内容仍保留在缓冲区。
- 关闭页面或切换工作区时，如果仍有未保存或自动保存失败内容，仍会提示用户。

### 当前处理建议

该需求适合作为编辑体验增强独立实现。建议先实现单文件自动保存和冲突保护，再评审是否增加全局设置、每工作区设置或快捷开关。

### 实现记录

- 文本编辑后进入等待自动保存状态。
- 停止输入约 1 秒后自动保存。
- 保存中、保存失败、版本冲突等状态在编辑工具栏和 notice 中反馈，继续沿用版本冲突保护。

## B-005: 文件树区分 Git 受控和未受控文件

### 状态

- 提出日期：2026-07-22
- 状态：已实现
- 优先级：中

### 背景

当前文件树已经可以展示 Git 变更状态，例如 modified、added、deleted、renamed、untracked、conflicted，也能在目录上展示子孙变更标记。但这些标记只覆盖“发生变化”的文件。对于没有变更但已被 Git 跟踪的文件，以及不属于任何 Git 仓库或未纳入 Git 跟踪的文件，文件树中没有明显区分。

在多子仓库工作区中，用户打开聚合目录时更需要知道每个文件或目录是否属于某个受控 Git 项目，否则容易误判某些文件是否会进入版本管理。

### 问题现象

用户在工作区文件树中只能看到“有变更”的 Git 标记，无法直接区分：

- 已被 Git 跟踪但当前干净的文件。
- Git 仓库中的未跟踪文件。
- 不在任何 Git 仓库覆盖范围内的普通文件或目录。
- 聚合工作区中属于哪个子仓库的文件或目录。

这会导致以下问题：

- 用户不知道当前看到的文件是否已经被版本管理。
- 新增文件如果没有进入 Git 跟踪，容易被忽略。
- 聚合工作区下多个子项目并列时，目录是否受控不直观。
- Git 修改列表和文件树之间缺少“受控范围”的视觉对应关系。

### 需求整理

希望在文件树中增加受控状态标识，让用户能快速判断文件或目录的 Git 管理状态。

至少应支持以下状态：

- 已受控：文件已被某个 Git 仓库跟踪，当前没有变更。
- 已受控且有变更：继续使用现有 M/A/D/R/C 等变更标记。
- 未跟踪：位于 Git 仓库内，但尚未被 Git 跟踪。
- 未受控：不属于任何已发现 Git 仓库覆盖范围。
- 子仓库根目录：明确标记该目录是一个 Git 项目根目录。

### 交互建议

1. 在文件树条目右侧增加轻量标记，例如 `T` 表示 tracked、`U` 表示 untracked、`-` 或灰色图标表示不在 Git 受控范围。
2. 对子仓库根目录使用更明显的标记，例如 Git 图标、`repo` 标签或特殊颜色。
3. 鼠标悬停时通过 tooltip 展示完整说明，例如“已受控：imv2-server”“未跟踪”“不在 Git 仓库中”。
4. 目录状态可以基于子孙文件聚合展示，例如“目录内存在未跟踪文件”或“目录属于 imv2-server 仓库”。
5. 可考虑增加文件树筛选或开关：显示未受控文件、只看未跟踪、只看有变更。

### 影响范围

- 后端文件树接口需要返回更完整的 Git 管理状态，不能只返回变更状态。
- `src/shared/contracts.ts` 的 `FileTreeEntry` 可能需要增加字段，例如 `gitTrackedState`、`repositoryId`、`repositoryPath` 或 `repositoryRoot`。
- `src/server/app.ts` 当前文件树 Git 标记逻辑需要区分 tracked、untracked、outside repository 和 repository root。
- `src/server/services/git-service.ts` 可能需要增加批量判断 tracked 文件的能力，避免对每个文件单独执行 Git 命令。
- `src/web/App.tsx` 文件树渲染需要展示新标记和 tooltip。
- `src/web/styles.css` 需要补充受控状态、未受控状态和仓库根目录的视觉样式。

### 技术建议

- 对当前目录下的可见条目批量计算受控状态，避免递归扫描整个工作区。
- 对每个已发现仓库，先判断文件树条目是否落在该仓库路径范围内。
- 对仓库内条目，可用批量 `git ls-files` 或类似机制判断 tracked/untracked/ignored 状态。
- 对目录可先标记“位于某仓库内”，子孙聚合状态后续再增强。
- 保持现有变更标记优先级：conflicted、modified、added、deleted、renamed、untracked 等仍优先展示。

### 验收标准

- 已被 Git 跟踪且当前干净的文件，在文件树中有明确“已受控”标记。
- 位于 Git 仓库内但未被跟踪的文件，在文件树中有明确“未跟踪”标记。
- 不在任何 Git 仓库覆盖范围内的文件或目录，有明确“未受控”标记。
- 子仓库根目录有明显标记，用户能看出它是一个 Git 项目。
- 多子仓库工作区中，不同子仓库下的文件能正确归属到对应仓库。
- 现有 M/A/D/R/C 等变更状态不被新标记破坏。
- 文件树懒加载仍然可用，打开大型目录不会因为受控状态计算明显卡顿。
- ignored 文件在默认隐藏策略下仍按现有规则处理。

### 当前处理建议

该需求适合作为文件树 Git 可视化增强独立实现。建议先实现“当前可见目录条目”的受控状态展示，再评审是否增加目录聚合状态和筛选能力。

### 实现记录

- 文件树接口返回 `gitTrackedState`、`repositoryId`、`repositoryPath`、`repositoryName`。
- 前端用 `repo`、`T`、`U`、`-` 标识仓库根、已跟踪、未跟踪和未受控。
- tooltip 展示当前条目的 Git 归属说明。

## B-006: 工作区文件列表和编辑区支持左右拖拽调整宽度

### 状态

- 提出日期：2026-07-22
- 状态：已实现
- 优先级：中

### 背景

当前工作区主界面采用固定列宽布局：左侧活动栏、文件列表/侧边栏、右侧编辑区。文件列表和编辑区之间没有可拖拽分隔条，用户无法根据当前任务调整两侧视框大小。

### 问题现象

在以下场景中，固定宽度会影响使用效率：

- 文件路径较长时，左侧文件列表显示不完整。
- Git 修改列表或历史列表内容较长时，侧边栏宽度不够。
- 编辑代码或查看 Diff 时，用户希望扩大编辑区。
- 查看目录结构时，用户希望临时扩大文件树。
- 不同屏幕尺寸下，固定宽度无法满足不同用户习惯。

### 需求整理

希望工作区的文件列表/侧边栏与编辑区之间支持左右拖拽调整宽度。

至少应支持：

- 鼠标拖拽侧边栏和编辑区之间的分隔条。
- 拖拽时实时调整文件列表/侧边栏宽度。
- 编辑区自动占用剩余空间。
- 设置最小宽度和最大宽度，避免拖到不可用状态。
- 调整后的宽度在当前浏览器中持久化，下次打开应用继续使用。
- 双击分隔条可恢复默认宽度。

### 交互建议

1. 在侧边栏右边缘显示细分隔条。
2. 鼠标悬停时显示可拖拽光标和高亮状态。
3. 按住拖拽时禁用文本选择，避免误选文件名或编辑器内容。
4. 拖拽过程中 Monaco 编辑器需要触发布局刷新，避免编辑器尺寸不更新。
5. 如果侧边栏宽度被调整过，可在设置或双击分隔条时恢复默认值。

### 影响范围

- `src/web/App.tsx` 主布局需要增加拖拽状态和分隔条元素。
- `src/web/styles.css` 中 `.app-shell` 当前固定 `grid-template-columns` 需要改为可变 CSS 变量。
- 需要将侧边栏宽度保存到 `localStorage`。
- Monaco 编辑器需要在宽度变化后正常重新布局。
- 文件树、Git 修改、Git 历史三个侧边栏视图都应共享同一个宽度。
- 移动端窄屏应禁用拖拽分隔条，避免和触摸滚动冲突。

### 技术建议

- 使用 CSS 变量，例如 `--sidebar-width` 控制主网格列宽。
- 默认宽度沿用当前 `290px`。
- 建议最小宽度 `180px`，最大宽度可取 `min(520px, 60vw)`。
- 拖拽事件使用 `pointerdown`、`pointermove`、`pointerup`，支持鼠标和触控设备，但移动端默认禁用。
- 拖拽结束后写入 `localStorage`，拖拽过程中只更新内存状态。

### 验收标准

- 桌面端可以通过拖拽分隔条调整文件列表/侧边栏宽度。
- 拖拽时编辑区宽度实时变化，页面不出现异常横向溢出。
- 文件树、Git 修改、Git 历史视图都使用调整后的侧边栏宽度。
- 刷新页面后，侧边栏宽度保持上次设置。
- 双击分隔条后恢复默认宽度。
- 侧边栏不能被拖到小于最小宽度，也不能超过最大宽度。
- 拖拽过程中不会误触发文件打开、目录展开或文本选择。
- 移动端布局不显示或不启用拖拽分隔条。

### 当前处理建议

该需求适合作为桌面端布局体验增强独立实现。实现时应优先保证现有三栏布局稳定，再考虑后续是否支持更多面板的拖拽分栏。

### 实现记录

- 主布局增加侧边栏拖拽分隔条。
- 侧边栏宽度使用 CSS 变量实时调整，并持久化到 `localStorage`。
- 双击分隔条可恢复默认宽度，移动端隐藏拖拽分隔条。

## B-007: Git 受控模块展示变更文件数量

### 状态

- 提出日期：2026-07-22
- 状态：已实现
- 优先级：中

### 背景

当前文件树已经能识别 Git 仓库根目录，并用 `repo` 标记提示该目录是一个受控模块。顶部也有 Git 受控项目下拉列表，打开页有最近工作区列表。但用户在聚合工作区中通常会同时看到多个子项目仓库，只看到仓库名称还不足以判断哪个仓库存在变更、哪个工作区需要关注、是否需要进入该模块查看修改或走提交流程。

### 问题现象

用户打开工作区后，需要逐个切换 Git 项目或进入 Git 修改面板，才能知道每个受控模块是否有变更。

典型问题：

- 多个子仓库并列时，不知道哪个仓库有未提交修改。
- 仓库根目录虽然有 `repo` 标记，但没有变更数量提示，无法快速判断关注优先级。
- 用户需要点击仓库选择器、打开工作区或进入 Git 修改视图后才能确认是否需要提交。
- 聚合目录中受控模块较多时，逐个查看成本高。
- 最近工作区列表只展示路径，无法提示该工作区下是否有受控项目存在变更。

### 需求整理

希望在文件树、Git 受控项目下拉列表、工作区列表中都展示变更文件数量，让用户在进入详情前即可判断哪些模块或工作区需要关注。

至少应支持：

- 在每个 Git 仓库根目录旁展示当前仓库变更文件总数。
- 在 Git 受控项目下拉列表中，每个受控项目条目展示对应仓库的变更文件总数。
- 在工作区列表中展示该工作区内受控项目的变更汇总数量。
- 计数口径基于该仓库 `git status` 的变更文件数量。
- 变更数量应包含已暂存、未暂存、未跟踪和冲突文件。
- 没有变更时不展示数量，或展示低干扰的 `0` 状态，最终以界面评审为准。
- 数量展示应和现有 `repo` 标记组合，不破坏当前 Git 受控状态标识。
- 鼠标悬停时展示完整说明，例如“Git 项目：imv2-server，3 个变更文件”或“该工作区共 2 个受控项目存在 8 个变更文件”。

### 交互建议

1. 文件树加载到 Git 仓库根目录时，在 `repo` 标记旁展示一个数量徽标。
2. Git 受控项目下拉列表中，在项目名称或路径右侧展示数量徽标。
3. 工作区列表中，在工作区名称或路径右侧展示汇总数量徽标。
4. 数量大于 0 时使用更醒目的颜色，例如黄色或蓝色，提示该仓库或工作区需要关注。
5. 数量为 0 时保持弱化，避免干扰正常浏览。
6. 点击仓库根目录仍保持现有文件夹展开行为。
7. 后续可考虑点击数量徽标直接切换到对应 Git 项目的“Git 修改”视图，但本期不强制。

### 影响范围

- 后端文件树接口需要在仓库根目录条目中返回变更数量。
- `src/shared/contracts.ts` 的 `FileTreeEntry` 可增加字段，例如 `repositoryChangedFileCount`。
- `GitRepositoryInfo` 或工作区 Git 汇总接口需要返回每个仓库的变更数量，例如 `changedFileCount`。
- 最近工作区列表如要展示数量，需要新增轻量接口批量获取工作区变更汇总，避免打开页逐个完整打开 watcher。
- `src/server/app.ts` 当前文件树 Git 标记逻辑可复用已获取的 `GitStatusSnapshot.files.length`。
- `src/web/App.tsx` 文件树、受控项目下拉列表、最近工作区列表渲染需要展示变更数量徽标。
- `src/web/styles.css` 需要补充数量徽标样式。

### 技术建议

- 优先只在 `entry.path === repository.workspacePath` 的仓库根目录条目上设置数量。
- 数量使用 `snapshot.files.length`，即 Git 状态中受影响文件的去重列表数量。
- 需要确保多仓库工作区中，每个仓库根目录展示自己仓库的数量。
- 受控项目下拉列表应直接使用仓库级数量，避免用户必须切换当前仓库后才能看到。
- 工作区列表展示汇总数量时，建议包含两个值：存在变更的仓库数和变更文件总数；界面空间不足时优先展示变更文件总数。
- 工作区列表的数量获取应懒加载或缓存，避免打开页一次性扫描大量历史工作区造成卡顿。
- 如果某个仓库 Git 状态读取失败，应不展示数量，并保留现有错误兜底，不影响文件树加载。
- 默认不对普通目录做递归数量聚合，避免误导和增加计算成本。

### 验收标准

- Git 仓库根目录存在变更时，文件树根目录条目展示变更文件数量。
- Git 受控项目下拉列表展示每个受控项目的变更文件数量。
- 工作区列表展示每个工作区的变更汇总数量。
- 多子仓库工作区中，每个仓库根目录展示各自的变更数量。
- 多子仓库工作区中，受控项目下拉和工作区列表的汇总数量与各仓库实际状态一致。
- 已暂存、未暂存、未跟踪、冲突文件都计入数量。
- 干净仓库不会被错误标记为有变更。
- 数量展示不会影响文件夹展开、右键菜单、删除、重命名等现有操作。
- 数量展示不会影响受控项目选择、工作区打开和最近工作区删除等现有操作。
- Git 状态变化后，数量会随现有 watcher 或刷新机制更新。
- Git 状态读取失败时，文件树仍可正常展示。

### 当前处理建议

该需求适合作为 Git 可视化的小迭代实现。建议先打通仓库级变更数量字段，并同时复用到文件树仓库根目录和受控项目下拉列表；工作区列表如涉及历史路径扫描，应优先做懒加载和缓存，避免影响打开页性能。

### 实现记录

- 工作区和 Git 仓库信息返回 `changedFileCount`，工作区返回 `changedRepositoryCount`。
- 文件树 Git 仓库根目录返回并展示 `repositoryChangedFileCount`。
- Git 受控项目下拉列表和当前受控项目摘要展示变更文件数量。
- 最近工作区列表通过轻量汇总接口展示每个工作区的变更汇总数量。
