## 说明原因

### 已确认：HTTP 未强制跳转 HTTPS

- `http://workspace.foxhello.cn/` 返回 `200` 和登录页，没有 `Location`，没有 `301/308` 跳转。
- `https://workspace.foxhello.cn/` 返回 `200`，curl 使用系统信任库验证成功，`ssl_verify_result=0`；浏览器也正常显示登录页。
- 证书由 Google Trust Services WE1 签发，覆盖 `*.foxhello.cn`；有效期为 2026-10-05 18:11:42 UTC 至 2027-01-03 19:10:31 UTC。
- HTTPS 响应未包含 `Strict-Transport-Security`。本次登录页未发现 HTTP 的 `src/href` 元素，浏览器诊断日志没有错误或警告；未对登录后所有资源做混合内容审计。

因此，在 HTTP 地址看到“不安全”提示有直接解释。当前没有证据表明 HTTPS 证书过期或域名不匹配。HTTP 页面上的密码传输也确实没有 TLS 保护。

### 已确认：首屏的外网访问开销显著

表中独立请求使用新建连接；域名直连采样每项 3 次，代理采样每项 2 次。它们不是浏览器 FCP，也不能直接相加代表实际首屏时间。

另一次按“HTML → JS → 登录状态 API”顺序、复用同一 HTTPS 连接的 curl 测量，三步分别约 2.64 / 0.74 / 0.57 秒，总计约 3.95 秒，说明连接复用后仍有明显等待。

- 直连请求的 `CF-RAY` 后缀为 `AMS`（阿姆斯特丹）；当前本机代理请求为 `NRT`（东京）。代理开启情况已通过系统配置确认，不能把直连采样等同于用户浏览器路径。
- 本机 cloudflared 近期的连接注册日志为 `lax*`（洛杉矶），并使用 QUIC。今天 14:15–14:16（北京时间）出现多条连接超时与重连记录。
- 以上确认了 Cloudflare 访问及 Tunnel 回源链路的开销与既往抖动；目前不能精确拆分浏览器到边缘、Cloudflare 内网和 Tunnel 的各段占比，也不能据此断言每次慢都是 QUIC 重连造成的。
- DNS 在本次重复直连请求中为数毫秒级，不是这些样本的主要等待。

### 已确认：登录后的统计接口还有源站开销

仅统计 2026-11-02 源站日志，`/api/workspaces/change-summary` 共 5 个完成请求，中位处理时间约 2.27 秒，最高 5.00 秒。该接口在最近工作区页面自动请求，每次为各路径新建 WorkspaceService，打开并扫描仓库，再读取变更数量。

这会拖慢最近列表的统计信息；界面并未等待统计完成才显示，不能把这 5 秒都算成白屏时间。

14:45:55 的 `/api/git/worktrees` 有进入源站的日志，14:45:59 Tunnel 记录该请求被取消；本次未找到对应完成记录。取消可能来自客户端离开或中断，不能仅凭 `context canceled` 判定服务端故障。历史完成请求曾有 7 秒耗时，需针对用户实际工作区另做专项分析。

## 当前代码问题点

- 登录首屏已有按需加载、HTML 内联等待画面、gzip/Brotli 预压缩和哈希资产一年缓存。本次实际看到入口资产 `MISS → HIT`，gzip 传输约 64 KB；当前入口没有回退为旧的 3.6 MB 大包。
- 登录状态判断在入口 JS 下载执行后发起；等待 API 完成后才显示登录表单，高往返延迟会沿依赖链积累。
- 应用没有针对公网域名的 HTTPS 重定向；`x-forwarded-proto` 当前仅用于 Cookie 的 Secure 属性判断。
- 最近路径统计只有前端短期缓存，服务端每次重新扫描。Worktree 总览则刷新全部分组后，按组处理，每组中每批最多并发 4 个 Worktree，并等全部完成后返回。

## 修改方案

1. 优先为该主机配置边缘重定向：匹配 `http.host eq "workspace.foxhello.cn" and http.request.scheme eq "http"`，返回 301/308 到同域名 HTTPS，保留路径与查询参数。可以配置单域名规则；若整区所有域名均支持 HTTPS，也可统一启用 Always Use HTTPS。Automatic HTTPS Rewrites 不替代顶层导航跳转。
2. HTTPS 跳转及所有页面验证稳定后，为该主机启用 HSTS；初期使用短有效期验证。不要未经核实将其他子域名纳入策略。
3. 先针对实际浏览器代理路径和 Tunnel 出口做对照采样，优先改善高延迟、丢包或 QUIC 超时的线路。只有在证实 QUIC 线路存在问题后，再评估 HTTP/2 传输的对照试验；不把切协议当成已证实修复。
4. 若需要持续改善远程首屏，将公开静态 HTML/资产放到更合适的边缘托管位置，减少首屏经过本机 Tunnel 的回源；维持同源 Worker 和 API/WebSocket 转发。缓存策略必须独立处理 HTML 更新与部署失效，鉴权和私有 API 继续 `no-store`。
5. 最近路径统计增加源站缓存与请求合并，按需/后台刷新，限制并发扫描；Worktree 总览可先返回基本清单，再按组读取状态。保留当前已有的首屏拆包和压缩优化。

本机 Tunnel 转发到 `http://localhost:43110` 属于本机回环段；公网 HTTPS 可以在 Cloudflare 终止，再经加密 Tunnel 访问该回环地址。它本身不等于浏览器在使用 HTTP，不应直接把该地址改成源站尚未提供的 HTTPS。

## 验证方式

- HTTP 请求应变为 301/308，`Location` 使用同域名 HTTPS，并保留路径与查询参数。
- HTTPS 使用正常证书校验，页面、API 及 WSS 均可访问；确认登录 Cookie 带 Secure。
- 按相同代理模式、相同缓存状态比较 HTML 首包、入口 JS 和登录状态接口；浏览器指标需另采真实导航时间。
- 优化统计后，比较最近路径相同、仓库状态相同情况下的源站处理时间和重复请求命中率。

限制：只在本机和当前网络采样，没有多地区测速，也没有为诊断登录、扫描或修改用户的实际工作区。Python 自带 CA 库的验证在本机报缺少签发链，未将该工具的本地信任库问题当成站点证书故障；证书结论以系统 curl 成功校验和浏览器成功加载为准。
